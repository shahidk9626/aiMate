1. Backend module boundaries

Identity & access

Registration, login, refresh, logout, password hashing, memberships, RBAC and tenant context.

Tenants & settings

Business profile, timezone, locale, working hours, team membership and configuration.

Channels

Channel connection lifecycle, provider account mapping, encrypted credentials and health state.

Webhook ingress

Signature verification, payload validation, provider normalization, idempotency and fast acknowledgement.

CRM

Contacts, leads, stages, assignment, notes, tasks and source attribution.

Inbox

Conversations, messages, read state, assignment, internal notes and human takeover.

AI orchestration

Context assembly, retrieval, policy checks, structured tool calls, response validation and escalation.

Outbound delivery

Provider adapters, rate-limit handling, retries, delivery receipts and message status.

Outbox & workers

Transactional outbox relay, Celery tasks (idempotent, acks late, bounded retries, dead-letter state).

Audit

Append-only audit log of security-relevant actions; written by services, never by route handlers directly.

3. Relational data model

Conventions: UUIDv7 primary keys; created_at/updated_at TIMESTAMPTZ; enums as VARCHAR + CHECK. Every tenant-owned table has tenant_id, UNIQUE(tenant_id, id), composite foreign keys (tenant_id, x_id) and Row Level Security. Column-level detail: docs/DATABASE_SCHEMA.md.

GLOBAL
users            id, email CITEXT UNIQUE, password_hash (Argon2id), full_name,
                 is_active, is_platform_admin, email_verified_at, last_login_at
tenants          id, name, slug CITEXT UNIQUE, timezone, locale,
                 status (trial|active|suspended|cancelled), settings JSONB
auth_sessions    id, user_id, family_id, refresh_token_hash UNIQUE, expires_at,
                 rotated_at, revoked_at            -- reuse of rotated token revokes family
password_reset_tokens  id, user_id, token_hash UNIQUE, expires_at, used_at
webhook_events   id, provider, dedupe_key, tenant_id NULL, channel_id NULL, payload,
                 status, attempts  · UNIQUE(provider, dedupe_key)
outbox_events    id, tenant_id NULL, event_type, payload, status, attempts, available_at
audit_logs       id, tenant_id NULL, actor_user_id NULL, action, resource_type,
                 resource_id NULL, metadata, ip           -- append-only

TENANT-OWNED (RLS)

5. Website enquiry sequence

Widget loads
Website embeds a tenant-scoped public widget key; API checks the channel’s origin allowlist and returns public widget configuration only.
Visitor session
API issues a signed, short-lived visitor token bound to that channel and visitor. Every later call needs it, so one visitor can never read another visitor’s conversation (the Origin header alone is forgeable).
Visitor sends a message
API validates token, rate limit, payload size and client_message_id (idempotency); optional bot check; creates or resumes a conversation.
Persist inbound message
Store message and an idempotency key in a transaction; create/update contact and lead.
Queue AI task
Commit event to an outbox table; worker picks it up after commit.
Build safe context
Load tenant knowledge, conversation history and agent policy; exclude unrelated tenant data.
Generate and validate answer
AI returns structured response; enforce policy, confidence threshold and handoff rules.
Deliver response
Persist outbound message as queued; worker sends via channel adapter and records result.
Update CRM + notify
Update lead qualification/status and notify assigned team when needed.

6. Meta webhook sequence

Provider sends webhook
Verify signature against raw request body using app secret; do not parse and reserialize before signature check.
Resolve channel and tenant
Map provider page/account ID to the one active channel record (globally unique per provider account).
Deduplicate event
Meta batches several entries per delivery and sends no event id, so a dedupe key is derived per message (mid) or per event hash and inserted under UNIQUE(provider, dedupe_key); duplicate deliveries return success without repeating side effects.
Acknowledge quickly
Return 200 after durable acceptance; perform AI and CRM work asynchronously.
Process asynchronously
Normalize event, upsert contact, append message, update conversation and create/update lead.
Reply only when allowed
Check provider-specific messaging windows, permissions, policy and account status before outbound delivery.

8. Tenant security and authorization

Authentication

Argon2id passwords; 15-minute access JWT; opaque rotating refresh token stored hashed; secure, HttpOnly, SameSite=Lax cookies; CSRF header + Origin check; one trusted browser origin (CORS).

Authorization

Resolve tenant membership on every request. Role checks in service layer, not just frontend route guards.

Database safety

Tenant-scoped repositories, composite constraints and PostgreSQL Row Level Security on every tenant table (implemented in Stage 1). The app connects as a role without superuser, BYPASSRLS or DDL rights; each transaction sets the verified tenant id; no tenant set means no rows.

Secrets

Envelope encryption for Meta tokens, key rotation, least privilege and no secrets in logs or client bundles.

Abuse protection

Rate limits, widget origin allowlist, payload size limits, bot controls and webhook verification.

Auditability

Record login, permission changes, channel connect/disconnect, exports and sensitive admin actions.

9. Error handling and reliability

FailureExpected handling
Duplicate webhookUnique idempotency key; no duplicate CRM or AI action.
AI provider timeoutBounded retry; fallback acknowledgement or human handoff.
Meta rate limitRespect Retry-After; exponential backoff with jitter.
Outbound send failurePersist failed state and provider error; retry only when safe.
Worker crashDurable queue/outbox, visibility timeout and retry policy.
Tenant mismatchReject request; log security event without leaking record existence.

Use transactional outbox for database-to-queue consistency. Do not rely on an in-memory background task for durable message processing.
