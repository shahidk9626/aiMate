3. Relational data model

All tenant-owned tables carry tenant_id. Composite foreign keys or equivalent database constraints should prevent cross-tenant references; API authorization is still mandatory.

users
- id UUID PK
- email CITEXT UNIQUE
- password_hash TEXT
- full_name VARCHAR
- is_active BOOLEAN
- created_at TIMESTAMPTZ

tenants
- id UUID PK
- name VARCHAR
- slug CITEXT UNIQUE
- timezone VARCHAR
- status ENUM
- created_at TIMESTAMPTZ

memberships
- id UUID PK
- tenant_id UUID FK -> tenants.id
- user_id UUID FK -> users.id
- role ENUM(owner, admin, agent)
- UNIQUE(tenant_id, user_id)

channels
- id UUID PK
- tenant_id UUID FK
- provider ENUM(instagram, facebook, website)
- display_name VARCHAR
- external_account_id VARCHAR
- credentials_ciphertext BYTEA
- status ENUM(pending, active, error, disconnected)
- settings JSONB
- UNIQUE(tenant_id, provider, external_account_id)

contacts
- id UUID PK
- tenant_id UUID FK
- full_name VARCHAR NULL
- email CITEXT NULL
- phone VARCHAR NULL
- external_identity VARCHAR NULL
- metadata JSONB
- created_at, updated_at TIMESTAMPTZ

leads
- id UUID PK
- tenant_id UUID FK
- contact_id UUID FK
- assigned_user_id UUID NULL
- title VARCHAR
- status ENUM(new, contacted, qualified, won, lost)
- source ENUM(instagram, facebook, website, manual)
- estimated_value NUMERIC(12,2) NULL
- qualification JSONB
- created_at, updated_at TIMESTAMPTZ

conversations
- id UUID PK
- tenant_id UUID FK
- channel_id UUID FK
- contact_id UUID FK
- lead_id UUID NULL
- external_thread_id VARCHAR NULL
- status ENUM(open, pending, closed)
- assigned_user_id UUID NULL
- last_message_at TIMESTAMPTZ
- UNIQUE(tenant_id, channel_id, external_thread_id)

messages
- id UUID PK
- tenant_id UUID FK
- conversation_id UUID FK
- provider_message_id VARCHAR NULL
- direction ENUM(inbound, outbound)
- sender_type ENUM(customer, ai, agent, system)
- body TEXT
- payload JSONB
- delivery_status ENUM(received, queued, sent, delivered, failed)
- created_at TIMESTAMPTZ
- UNIQUE(tenant_id, provider_message_id)

webhook_events
- id UUID PK
- provider VARCHAR
- provider_event_id VARCHAR
- tenant_id UUID NULL until resolved
- payload JSONB
- status ENUM(received, processing, processed, failed)
- received_at, processed_at TIMESTAMPTZ
- UNIQUE(provider, provider_event_id)

audit_logs
- id UUID PK
- tenant_id UUID
- actor_user_id UUID NULL
- action VARCHAR
- resource_type VARCHAR
- resource_id UUID
- metadata JSONB
- created_at TIMESTAMPTZ
Design note: use a separate contacts table and leads table. A person can enquire more than once and create multiple opportunities. Do not assume phone/email is always available: social identities may be the only identifier.

5. Website enquiry sequence

Widget loads
Website embeds a tenant-scoped public widget key; API returns public widget configuration only.
Visitor sends a message
API validates origin, rate limit, payload size and widget key; creates or resumes a conversation.
Persist inbound message
Store message and an idempotency key in a transaction; create/update contact and lead.
Queue AI task
Commit event to an outbox table; worker picks it up after commit.
Build safe context
Load tenant knowledge, conversation history and agent policy; exclude unrelated tenant data.
Generate and validate answer
AI returns structured response; enforce policy, confidence threshold and handoff rules.
Deliver response
Persist outbound message as queued; worker sends via channel adapter and records result.
Update CRM + notify
Update lead qualification/status and notify assigned team when needed.

6. Meta webhook sequence

Provider sends webhook
Verify signature against raw request body using app secret; do not parse and reserialize before signature check.
Resolve channel and tenant
Map provider page/account ID to an active channel record.
Deduplicate event
Insert provider event/message ID under a unique constraint; duplicate deliveries return success without repeating side effects.
Acknowledge quickly
Return 200 after durable acceptance; perform AI and CRM work asynchronously.
Process asynchronously
Normalize event, upsert contact, append message, update conversation and create/update lead.
Reply only when allowed
Check provider-specific messaging windows, permissions, policy and account status before outbound delivery.

  -> ActionRouter
       |-- reply_to_customer

GuardrailImplementation rule
GroundingAnswer business-specific questions from approved knowledge; say when information is unavailable.
ActionsLLM proposes typed actions; backend validates permissions and inputs before execution.
HandoffEscalate on low confidence, complaint, sensitive request, explicit human request or unsupported intent.
Prompt injectionTreat customer messages and uploaded knowledge as untrusted data, not system instructions.
Cost controlPer-tenant token/message limits, model routing, usage ledger and rate limits.

8. Tenant security and authorization

Authentication

Short-lived access tokens; refresh token rotation; secure, HttpOnly, SameSite cookies for browser sessions.

Authorization

Resolve tenant membership on every request. Role checks in service layer, not just frontend route guards.

Database safety

Tenant-scoped repositories and composite constraints. Consider PostgreSQL row-level security as defense in depth.

Secrets

Envelope encryption for Meta tokens, key rotation, least privilege and no secrets in logs or client bundles.

Abuse protection

Rate limits, widget origin allowlist, payload size limits, bot controls and webhook verification.

Auditability

Record login, permission changes, channel connect/disconnect, exports and sensitive admin actions.

9. Error handling and reliability

FailureExpected handling
Duplicate webhookUnique idempotency key; no duplicate CRM or AI action.
AI provider timeoutBounded retry; fallback acknowledgement or human handoff.
Meta rate limitRespect Retry-After; exponential backoff with jitter.
Outbound send failurePersist failed state and provider error; retry only when safe.
Worker crashDurable queue/outbox, visibility timeout and retry policy.
Tenant mismatchReject request; log security event without leaking record existence.

Use transactional outbox for database-to-queue consistency. Do not rely on an in-memory background task for durable message processing.
